# 踩坑清单

本文件记录开发过程中**实际踩到并解决**的坑。每一条都标注了现象、根因和规避方式，
用来避免重复排查，也是设计报告里「技能包提炼过程」的素材来源。

---

## 1. Vitis HLS 打不开含非 ASCII 字符的路径

**现象**

在 `D:\新建文件夹` 这类含中文的目录下运行 Vitis，报：

```
run_hls.tcl can't be opened.
command 'set_msg_logfile' returned error code
```

随后进程以非零码退出，看起来像脚本写错了，实际是路径编码问题。

**根因**

Vitis HLS 内部的 Tcl 解释器按本地代码页处理路径，非 ASCII 字符会解析失败。

**规避**

- 工作区必须是纯 ASCII 路径。程序默认把它放在**当前项目所在盘**的
  `<盘符>:/hls_work`（例如 `D:/hls_work`），既保证纯英文，又不会挤爆系统盘。
- 可用 `--workspace` 或环境变量 `HLS_AGENT_WORKSPACE` 覆盖。
- `hls_agent/config.py::resolve_workspace` 会主动校验，遇到非 ASCII 路径直接报错，
  而不是等到 Vitis 崩掉。

## 2. `csim.exe` 缺 DLL 会「静默退出」

**现象**

Vitis 的 `csim_design -setup` 报告成功、`csim.exe` 也生成了，但手工执行它时：

- **0.1 秒内退出**
- **stdout / stderr 全空**
- 没有任何错误信息

看起来像卡死或死循环，极难定位。

**根因**

Vitis 生成的 `csim.exe` 依赖浮点算子模型的 DLL（`fpo_v7_1` 等）和 MinGW 运行时
（`tps/mingw/.../bin`）。这些目录不在系统 PATH 里，进程加载失败即退出，
且失败发生在 C++ 运行时的输出机制就绪之前，所以**看不到任何报错**。

**规避**

正确的 PATH 列表由 Vitis 自己写在该 csim build 目录的 `env.json` 里：

```json
{"PATH": [".../win64/tools/fpo_v7_1", ".../tps/mingw/10.0.0/win64.o/nt/bin"]}
```

`hls_agent/vitis.py::csim_env` 会读取它并注入子进程环境。若 `env.json` 缺失，
则按 Vitis 安装布局推断。

## 3. 推理模型的 `max_tokens` 太小会让正文为空

**现象**

调用返回 HTTP 200，但正文一个字符都没有；错误信息形如
「模型只返回了思考内容，没有正文」。

**根因**

推理型模型（返回 `thinking` + `text` 两个 content 块）会先输出大量思考内容。
若 `max_tokens` 太小，预算在思考阶段就被耗尽，**正文块根本没来得及生成**。

**规避**

- 默认 `HLS_AGENT_MAX_TOKENS=16384`。
- `hls_agent/backends.py` 的响应解析会跳过 thinking 块；若正文为空但思考内容里
  含有代码，则回退使用思考内容，并给出明确报错（带 `stop_reason`）方便定位。

## 4. 定点运算不能按绝对误差比对

**现象**

生成的 `3mm` 相对参考输出的**最大绝对误差约 0.05**，看起来像算错了；但实际功能是对的。

**根因**

参考实现用 `D[i][j] *= beta;` 原地累加，生成的实现用局部变量累加后整体赋值。
两者数学等价，但 `ap_fixed<32,16>` 在每一步都做舍入，**舍入点不同**，
经过三次矩阵乘的累积后末位就差出 1e-3 量级。

**规避**

- 数值比对用**相对误差**（阈值 `1e-2`），不用绝对误差。
- 官方 HLS-Eval 的 zero-shot 评测**根本不比对 dump**，只看 csim 返回码；
  但 dump 型 testbench 不查数值，功能错误的代码也能「可运行」（见第 11、12 条）。
  因此本项目默认把 dump 比对纳入判定（`strict_dump`），`--official-pass` 可切回
  官方口径与排行榜对标。

## 5. MachSuite 变体：testbench 的相对路径数据文件必须放进运行目录

**现象**

全量评测时 `machsuite` 变体 **17/17 全部失败**，但 Vitis 日志里**没有任何编译错误**——
编译过了，运行才失败：

```
Assertion failed: in_fd > 0 && "Couldn't open input data file"
```

**根因（与最初的猜测不同）**

最初以为是 POSIX 头文件（`fcntl.h` / `unistd.h`）在 Windows 上不可用——**实际不是**，
这些头文件 Vitis 的 mingw 工具链都提供。真正的原因是：

testbench 用**相对路径**读 `input.data` / `check.data`：

```cpp
in_fd = open("input.data", O_RDONLY);
```

而 `csim.exe` 是以 **csim build 目录**为工作目录运行的
（`<proj>/solution__synth/csim/build/`），数据文件却在上一层的工作目录里，
相对路径自然找不到。注意这两个文件在数据集的 `hls_eval_config.toml` 里
是以 `tb_data` 声明的——爬到了声明却没用上运行目录这一环。

**规避**

`hls_agent/vitis.py::TaskPaths.stage_files` 记录这些数据文件，
`run_csim` 在运行 csim.exe 前把它们复制进 csim build 目录。修复后
`gemm_ncubed` 等题从「失败」变为「可运行」。

**教训**：这是**我们自己的流程 bug**，不是模型能力问题，也不是环境不支持。
全量评测的价值就在这里——17 道题（占全部失败的 38%）被误判成「模型做不出来」，
实际是评测脚手架漏了一步。**看到大面积同变体失败，先怀疑脚手架，再怀疑模型。**

## 6. 模型不一定遵守输出格式

**现象**

提示词要求输出 `<OUTPUT_CODE name="x.cpp">...</OUTPUT_CODE>`，但模型有时返回
带叙述文字的回答、markdown 围栏代码块，甚至直接输出裸代码。

**规避**

`hls_agent/llm.py::extract_source` 实现了五级回退：

1. 官方 `<OUTPUT_CODE>` XML 格式
2. ` ```xxx.cpp ` 文件名围栏
3. 含顶层函数名的围栏代码块
4. 任意像 C++ 的围栏代码块（取最长的）
5. 整段文本本身就是 C++

另外，**抽取失败也要重试**——早期版本遇到抽取失败直接放弃，白白浪费重试额度。

**现象**

按旧教程执行 `vitis_hls -f run.tcl` 提示找不到命令。

  在 Linux 上找 `vitis-run` / `vitis_hls`，并覆盖常见的安装目录。

## 8. 模型按 XML 格式输出时会把尖括号转义

**现象**

生成的 C++ 编译失败，报错：

```
2mm.cpp:3:9: error: use of class template 'ap_fixed' requires template arguments;
               argument deduction not allowed in typedef
```

去看生成的文件，发现里面是：

```cpp
typedef ap_fixed&lt;64, 32&gt; t_accum;      // 实际想要 ap_fixed<64, 32>
```

**根因**

提示词要求模型把代码放在 `<OUTPUT_CODE name="x.cpp">` 标签里。模型**正确地**遵守了
XML 语义——在 XML 里 `<` 必须转义成 `&lt;`。而我们的抽取器是正则匹配，
不做反转义，于是转义字符被原样写进了 `.cpp`，编译器把 `ap_fixed&lt;64,32&gt;`
解析成没有模板参数的 `ap_fixed`。

**注意**：官方 HLS-Eval 的 `extract_code_xml_from_llm_output` 也是正则实现、
同样不做反转义，所以这个问题在官方流程里也存在。

**规避**

`hls_agent/llm.py::unescape_xml_entities` 在抽取后统一还原。对所有回退路径
（XML / 围栏 / 裸代码）都生效。真实 C++ 代码里几乎不会出现字面的 `&lt;`，
因此还原的误伤风险极低。

**为什么容易漏**

这条坑是**跑批量评测时**才暴露的——单题手工验证时模型往往不转义，
只有在真实批量运行、模型状态不同时才出现。这说明「跑真实数据」比「跑通一遍」重要。

## 9. 「可编译」与「可运行」是两级，必须分开验证

**根因**

官方 `VitisHLSCSimTool` 的执行方式是：

1. `csim_design -setup` —— **只编译**，不运行
2. 手工执行生成的 `csim.exe` —— 才是运行

**规避**

`hls_agent/vitis.py::run_csim` 严格按这个顺序做，分别记录两个阶段的返回码，
对应赛道的「可编译」和「可运行」两级判定。若合并成一次 `csim_design`，
就丢失了中间判据。

## 10. 推理模型的思考 token 是生成时间的主要来源

**现象**

单题总墙钟 100~150 秒，其中模型生成占 70~90%。查看响应发现输出 token 里
`thinking` 块和正文差不多长甚至更长——思考内容对最终代码没有贡献，却占了一半以上
的生成时间。

**根因**

推理模型（本机网关底层是 `deepseek-v4-pro`）在输出正文之前会先生成大段思考，
按 token 计费也按 token 耗时。

**规避**

调用时传 `thinking: {"type": "disabled"}`（Anthropic Messages 接口），
或 `budget:N` 给思考限定预算。实测效果：

| 配置 | 2mm 生成耗时 | 2mm 总墙钟 | 结果 |
| --- | --- | --- | --- |
| 思考开启（默认） | 76~148 s | 100~148 s | 通过 |
| 思考关闭 | **5.2 s** | **27 s** | 通过，数值完全一致 |

即 **5 倍以上提速，质量无损失**（2mm/3mm/chstone 均已验证）。

本项目中通过 `HLS_AGENT_THINKING=off`（默认）/ `budget:N` 控制，
见 `serve/env.example` 与 `hls_agent/backends.py::_thinking_payload`。
若遇到难题质量下降，把该题改用 `budget:2048` 或开启思考重跑即可。

**注意**：切到本地模型（如 qwen2.5-coder）后行为会不同——有些模型没有思考模式，
有些（qwen3）通过 `think: false` 关闭。接入新模型时要实测一次耗时构成。

## 11. 定点统计类 kernel：数学等价的公式误差会差几个数量级

**现象**

批量评测中 correlation / covariance 两题「可运行」判定通过（csim 返回码 0），
但 dump 比对发现**功能错误**：

| 题目 | 最大相对误差 |
| --- | --- |
| correlation | 8153%（绝对值 81.5，参考值域 [0,1] 内） |
| covariance | 200% |

**根因**

这两题的 testbench 是 dump 型（只打印结果、不自校验），所以功能错误的代码
照样「可运行」——官方四级判定只看返回码，**这是官方口径的盲区**。

更深一层：参考实现用的是「**先归一化、后点积**」的算法——把 data 除以
`sqrt(n)*stddev` 后相关矩阵就是点积，**除法只发生一次**。模型生成的实现
在数学上完全等价，但用的是「协方差除以标准差乘积」：

```cpp
corr = (sum_cov / n) / (stddev_i * stddev_j);   // 两次除法 + 一次 sqrt
```

`ap_fixed<32,16>` 每一步都舍入：sqrt 有误差、两次除法误差叠加，
当 stddev 很小（数据方差小）时分母趋近 0，误差被放大到爆炸。

**规避**

1. **把 dump 比对升级为硬判据**：本项目默认 `strict_dump=True`（用
   `--official-pass` 可切回官方口径）。作为参赛队要保证功能正确，
   评测统计以「数值一致」为准，官方口径另列。
2. **重试提示词给参考数值样例**：只告诉模型「数值不符」没用，要附上
   「参考前 6 个值 vs 实际前 6 个值」和最大误差位置，模型能立刻判断是
   精度问题还是算法问题（`runner.py::_dump_mismatch_detail`）。
3. **提示词防患于未然**：涉及除法/开方的题目，提示词里提醒
   「定点下数学等价的公式误差差异巨大，除法合并成一次、先归一化后点积」。
4. 若重试仍修不好，把「参考实现的关键结构」（先归一化再点积、eps 保护分支）
   作为领域知识直接写进提示词——这正是技能包的价值。

## 12. dump 型 testbench 的盲区（第 11 条的姊妹篇）

**根因**

HLS-Eval 的 testbench 有两种：自校验型（内部 compare、失败返回非 0）和
dump 型（只把结果打印到 `==BEGIN DUMP_ARRAYS==` 块，由外部脚本比对）。
官方四级判定只看 csim 返回码，所以 dump 型题目「功能错误」也能通过。

**规避**

本项目把 dump 比对纳入判定（`strict_dump`），并把比对详情（逐数组误差、
最大误差索引、参考/实际前 6 个值）落进评测结果和重试提示词。
跑分时注意区分两个口径：

- 官方口径（`--official-pass`）：可运行 = 返回码 0，用于与排行榜对标
- 严格口径（默认）：可运行且数值一致，用于保证真实正确率

## 13. 不要试图绕过 Vitis 用别的编译器做快速验证（Windows）

**现象/结论**

想用 Vitis 自带的 mingw g++ 或 clang 直接编译内核+测试台，绕过 Vitis 工程启动
的 ~10 秒开销。实测：

- Vitis 的 clang-16 只 target `x86_64-pc-windows-msvc`，本机没有 MSVC SDK，
  直接调用要么报 DLL 缺失（`sqlite3.51.1.dll`），要么落到 C++IDE 的 STL 上报
  「STL1000: Unexpected compiler version」；Vitis 内部靠 `-hls` 特殊模式 +
  一整套环境变量才能工作，复刻成本高。
- mingw g++ 能编过且**数值结果与 Vitis csim 完全一致**（2mm 最大绝对误差同为
  0.054072），但编译耗时 **28 秒**（ap_fixed 模板实例化），比 Vitis 的 ~17 秒还慢。

**结论**：Windows 上「绕过 Vitis 加速编译验证」这条路不通。要降总时间，
去砍模型生成时间（见第 10 条，5 倍收益），Vitis 的 ~17 秒是工具固定成本。

## 14. 静态预检必须接在主循环里（写了工具但不接入等于没有）

**现象/结论**

`skill/check_generated.py`（毫秒级的静态预检）早就写好了，但主流程一直没用它：
生成代码后直接进 Vitis（~20s），编译失败才发现漏 include、签名不符这类
一眼就能看出的问题——每次失败白白等一次 Vitis 往返。

**规避**

把静态检查抽成 `hls_agent/static_check.py` 的核心实现（CLI 薄封装保留在 skill），
接入 `runner.py` 重试循环：生成后先静态预检，有阻断项直接把「人话」错误
（如「没有 #include "2mm.h"」）回灌模型，**不跑 Vitis**。配合重试温度 0.7
（避免模型重复同样错误）和 csim 超时收紧到 240s，失败路径的时间成本大幅下降。

**教训**：工具只有接进主流程才算数。写好的校验脚本束之高阁 = 每次失败多付
20 秒 × 失败次数的时间税。

## 15. Windows 本机的 Vitis 缺数学库 DLL（**`std::sqrt` 触发，不是 `hls::sqrt`**）

> **本条曾被误判并修正过。** 最初观察到 correlation（定点）用 `hls::sqrt` 崩溃，
> 就把 `hls::sqrt` 判成元凶，还据此写了一条「double 内核请用 std::sqrt」的提示词
> 规则——**方向完全相反**，导致 4 道 double 题从「能跑」变成「崩溃」。
> 下面是修正后的结论，教训见末尾。

**现象**

csim 编译照常通过，但运行 `csim.exe` 时**立即崩溃**：返回码 3221225781
（0xC0000135 = STATUS_DLL_NOT_FOUND），stdout/stderr 全空，
和「缺 DLL 静默退出」（第 2 条）是同一类症状。

**根因（经 pefile 解析导入表 + 对照实验确定）**

| 代码里的写法 | csim.exe 的额外依赖 | 结果 |
| --- | --- | --- |
| `hls::sqrt`（ap_fixed） | 无（模板内联展开） | ✅ 能跑 |
| **手写内联 sqrt** | 无 | ✅ 能跑，且**数值与参考完全一致（误差 0）** |
| **`std::sqrt` / 裸 `sqrt()`** | `libhlsm-GCC95-x64.dll` | ❌ 缺 DLL 崩溃 |

Vitis 的 csim 把 `std::` 数学函数链接到它自己的数学库，而运行时 DLL
（`libhlsm` / `libhlsmc`）**在整个 Vitis Windows 安装里都不存在**
（全盘搜索只能找到综合用的位码 `libhlsmc++_39.bc`）。

**规避**

1. **内核里避免 `std::` 数学函数和裸 `sqrt()/pow()`**，手写内联实现。
   开方用牛顿迭代即可，实测与参考实现**逐位一致**：
   ```cpp
   static double my_sqrt(double x) {
       if (x <= 0.0) return 0.0;
       double r = x;
       for (int i = 0; i < 60; i++) r = 0.5 * (r + x / r);
       return r;
   }
   ```
   `ap_fixed` 内核用 `hls::sqrt`（内联，安全）。
2. 静态预检对 `std::` 数学函数与裸 `sqrt/pow` 给出警告。
3. 这是 **Windows 开发机特有**；Linux 评测环境无此坑。
4. **必须区分「内核调用」和「测试台调用」**，两者的正确处理方式完全相反：
   - **内核调用**（如 `polybench__gramschmidt` 写了裸 `sqrt(norm)`）：**可修复**。
     2026-10-13 复现：同一台机器、同一套代码库，
     `polybench__cholesky`（手写 `my_sqrt`）与 `polybench__correlation`（手写内联）
     **均通过**，而 `polybench__gramschmidt`（裸 `sqrt()`）稳定以 0xC0000135 崩溃。
     所以 runner 把「改用内联实现」写成明确指示让模型重试，而不是一次失败就放弃。
   - **测试台调用**（如 `pp4fpga/pp4fpga_cordic/cordic_tb.cpp:36-37` 直接调用
     `sin((double)radian)` / `cos((double)radian)`）：测试台由数据集提供、
     **不可修改**，模型改内核无济于事，属于 Windows 硬限制，只能留到 Linux
     评测机验证——**不要在这种题上浪费重试额度**。
     runner 用 `_tb_needs_mathlib()` 自动识别并直接停止重试。

   > **本条曾有的错误结论**：早期写成「检测到 0xC0000135 + 零输出就判定环境受限并
   > 停止重试」。这在"测试台调用"时是对的，在"内核调用"时**是错的**——
   > 它把模型完全可修复的题直接判死，实测导致 polybench 变体里若干题无谓失败。

**教训（比坑本身更重要）**

1. **归因不能只看一次观察**。当时只看到「用了 hls::sqrt 的题崩了」就下结论，
   没做对照实验（「同样逻辑换一种写法还会不会崩」）。做了才发现方向反了。
2. **错误的知识进了提示词会主动造成伤害**。这条误判被写进技能包后，直接
   让 4 道题退步——技能包里的每条规则都应该有实验支撑，而不是推测。
3. 修正方式：静态预检里同时检查两种写法，提示词给出**实测过的**正确做法。

## 16. 定点饱和：输出里出现 ±32768 就是溢出，不是精度问题

**现象**

122 题全量评测中 16 道「数值不符」，其中定点变体的失败有共同指纹——实际输出
里出现**贴着 ±32768 的值**：

| 题目 | 实际值 | 参考值 |
| --- | --- | --- |
| lu | -32738.3 | 1.0 |
| trmm | -32754.6 | 1.75125 |

**根因**

`ap_fixed<32,16>` 共 32 位、其中 16 位是整数位（含符号），可表示范围约
**±2^15 = ±32768**。迭代/累加类内核（LU 分解、Jacobi 迭代、Gram-Schmidt、
三角求解）中间结果增长快，一旦越界就**饱和**到边界值，之后所有计算都是错的。

这与第 11 条的「除法误差放大」是**两类不同问题**：饱和是量级错误（差几万），
除法误差是精度错误（差 1e-3 量级）。

**规避**

1. **识别指纹**：输出里出现接近 ±32768 的值 → 判定为饱和，而不是舍入问题。
   `runner.py::_detect_saturation` 自动检测，命中时重试提示词直接给出
   「把中间累加换成 ap_fixed<64,32>」的修复方向。
2. **技能包提示词预防**：`AGENT_SKILL_SYSTEM` 第 5 条写明取值范围与饱和风险，
   让模型在生成时就用宽类型累加。
3. 注意区分变体：`polybench` 变体用 `double`，不会饱和；它那里的数值错误
   是**真算法错误**（实测某个 trmm 实际 0 vs 参考 6.175），需要从算法描述
   层面排查，不能套用定点经验。

**教训**：同样是「数值不符」，定点变体和 double 变体的根因完全不同。
分析失败时必须先看数据类型与误差量级，再决定用哪套修复策略。

## 17. CHStone 变体要求逐位一致，必须复刻参考算法而非自创等价算法

**现象**

`chstone` 变体 7 道失败，testbench 报的是**精确数值不匹配**：

```
df_mul64To128: a=0x100000000 b=0x100000000
               expected=(0x0000000000000001, 0) got=(0x0, 0)      → 算法错误
df_float64_ge: float64_ge(fff0000000000000, fff0000000000000)
               = 0, expected 1                                    → 边界处理错误
dfsin:         input=3fc65717fced55c1
               expected=3fc63a1a335aadcd output=3fc63a0ee11c1ca8  → 低位不匹配
```

**根因**

CHStone 是从真实软件实现抽取的 kernel（软浮点、大数运算、定点三角函数），
它的 testbench **逐位比对**（比较十六进制位模式，不是容差比对）。

模型倾向于写「一个数学上正确的实现」，但这些 kernel 的参考实现有特定细节：
查表法的具体表内容、series 展开的项数、进位处理顺序、边界值（0 / 全 1 /
负零 / NaN）的特殊分支。少任何一处，位模式就对不上。

注意 `dfsin` 那种「只差低位」的失败最容易被误判为精度问题——实际是算法项数
或舍入方式与参考不同。

**规避**

1. **提示词明确要求复刻**：`AGENT_SKILL_SYSTEM` 第 6 条写明「描述里提到的查表、
   常量表、移位次数、迭代次数必须照做；边界输入要按参考方式特殊处理」。
2. **区分三个变体的判定性质**：
   - `polybench`（double）：容差比对，算法对就行
   - `hls_polybench__fixed__small`（ap_fixed）：容差比对，但怕溢出/除法误差
   - `chstone`：**逐位比对**，必须复刻参考算法
3. 逐位不一致时，重试提示词要给足具体数值（哪个输入、期望什么、实际什么），
   模型才能定位到是哪个分支/表项出了问题。

**教训**：同样是「数值不符」，三个变体的根因和修复策略完全不同。
失败分析必须先看**变体的判定性质**（容差 vs 逐位）和**数据类型**
（double vs 定点），再决定策略——这也是把失败按变体分组统计的价值。

## 18. 评测机的睡眠会污染墙钟统计（看起来像卡死）

**现象**

MachSuite 重跑里 `stencil_stencil3d` 报告单次耗时 **36914 秒（10.25 小时）**，
其中「生成耗时 36904s」。但 LLM 调用超时明明设的是 300 秒——不可能真跑 10 小时。

看文件时间戳就明白了：

```
prompt.txt            写入于 00:41:43
raw_llm_output_1.txt  写入于 10:56:47   ← 中间隔了 10 小时
```

**根因**

机器（笔记本）在评测过程中**休眠**了。挂起期间：
- 墙钟（`time.time()`）继续走
- 模型请求其实早已发出并完成，只是响应在唤醒后才被写入
- Windows 上 `time.monotonic()` / `perf_counter()` 同样包含休眠时间，
  换时钟解决不了

**影响**

1. 耗时统计严重失真（平均值、最长值都不可信）
2. **按墙钟计算的总时间预算会把后续题目误判为超时**——这一次 `viterbi_viterbi`
   就被预算跳过了

**规避**

- **跑批量评测前关闭睡眠**（Windows：`powercfg /change standby-timeout-ac 0`，
  或把电源计划设为「高性能」并禁用休眠）。
- 报告耗时前先扫一遍：单题耗时若远超其各阶段之和（如生成耗时 >> 超时上限），
  就是休眠污染，应剔除该样本或重跑。
- 重新评测时优先补跑「被预算跳过」和「耗时异常」的题目，而不是重跑整批。

**教训**：长时后台任务要假设机器会休眠。评测这类一次性跑几十分钟的任务，
开跑前先改电源设置是零成本的保险。

## 19. 技能包知识必须按数据类型条件注入，否则会帮倒忙

**现象**

122 题 agent vs 基线对比中，总体增益 +4.1 个百分点（68.0% → 72.1%），
但 `polybench` 变体**反而退步 2 题**（68% → 61%）：

| 题 | 变体 | 基线 | 智能体 |
| --- | --- | --- | --- |
| polybench__lu | polybench（double） | 通过 | 失败 |
| polybench__jacobi-2d | polybench（double） | 通过 | 失败 |

**根因**

技能包提示词里有一条定点专用规则：

> Do NOT introduce `float` or `double` intermediates.

而 `polybench` 变体的内核**本来就用 `double`**（`void kernel_syrk(double alpha, ...)`）。
这条规则被无条件注入后，模型被引导去规避本该使用的 double，生成的代码反而错了。

**规避**

技能包知识**按题目实际数据类型分组注入**（`prompts.py::build_agent_skill_system`）：

| 分组 | 内容 | 注入条件 |
| --- | --- | --- |
| `AGENT_SKILL_COMMON` | 复刻算法、边界值处理 | 所有题目 |
| `AGENT_SKILL_FIXEDPOINT` | 除法合并、eps 保护、禁 float 中间量、±32768 饱和 | 仅当题头含 `ap_fixed` |

判断依据直接读题目的头文件（`"ap_fixed" in task.header_src`），零成本且准确。

**教训**

1. **「加知识」不等于「提升」**——错误的领域知识会让模型表现变差，
   而且只在对比基线时才暴露出来。这也再次说明基线对照的价值。
2. 技能包条目要**标注适用范围**。一条规则在 A 类题上是解药，在 B 类题上可能是毒药。
3. 做增益对比时**必须分变体看**。只看总体 +4.1% 会掩盖 polybench 的 -2，
   错失这个归因机会。

## 20. 输出被 `max_tokens` 截断时，抽取器会取到"讲解用代码片段"

**现象**

模型看起来"改了三次都没改对"，但翻工作区才发现：第 2、3 次尝试写进磁盘的
`dfadd.cpp` 只有 28 / 41 行，**没有 `#include`，函数体里是字面量 `...`**。

**证据**（`D:\hls_work\dfadd`，批次 `20261012_130807`，2026-10-13 复核）

| 原始输出 | 大小 | `<OUTPUT_CODE>` 开/闭 | 抽取结果 |
| --- | --- | --- | --- |
| `raw_llm_output_1.txt` | 11282 字符 | 1 / 1 | 11236 字符，335 行，含 `#include`，**完整** |
| `raw_llm_output_2.txt` | 59055 字符 | **0 / 0** | **774 字符，28 行，无 include，含 `...`** |
| `raw_llm_output_3.txt` | 51917 字符 | **0 / 0** | **1136 字符，41 行，无 include，含 `...`** |

**根因**

重试提示让模型"讲清楚为什么这么改"，模型于是写了 5 万多字符的分析，
在写到一半时撞上 `max_tokens` 上限被截断 —— 整个回复里**一个
`<OUTPUT_CODE>` 标签都没有**。

抽取器 `extract_source` 的回退链走到第 3 层「任意包含顶层函数名的围栏代码块」
时，正好命中模型在分析里随手贴的**示意片段**，于是把骨架当成实现写盘、
送进 Vitis。

更糟的是，这个失败会被记成"模型能力不足"，掩盖真实原因。

**规避**

1. **原文有 `<OUTPUT_CODE` 开标签、却没有闭标签** → 直接判定"输出被截断"，
   抛 `OutputTruncated`，不返回任何代码。
2. **抽出的代码里有整行 `...`** → 判定为骨架片段，同样拒绝。
   （真实的 HLS 内核里不会出现孤立的 `...` 行；`printf(const char*, ...)`
   的 stripped 内容不是孤立省略号，不会误判。）
3. 命中后走**纯格式重试**：要求"只输出代码块、不要写任何分析文字"，
   并**完全跳过 Vitis**——残片注定编译不过，没必要付一次 20~240 秒的工具往返。
4. 重试提示词（`prompts.py::RETRY_SUFFIX` 与 `NO_PROGRESS_SUFFIX`）现在都显式
   要求回复以 `<OUTPUT_CODE ...>` 开头、以 `</OUTPUT_CODE ...>` 结尾。

**教训**

1. **"模型没改对"和"模型的话没被完整听到"是两码事**。在把失败归因到模型能力
   之前，先确认**落盘的那份代码就是模型真正想给的那份**。
2. 抽取器的回退链**层次越多越危险**：每多一层，就多一次"取到看起来像代码、
   其实不是实现"的机会。回退必须配完整性校验。

## 21. `tb_data_hls_error.json` 不是容差，是"参考实现自身的偏差"

**现象**

失败反馈里出现一句自相矛盾的话：

> 数值与参考输出不符（**相对容差 0**）

而实际判定用的容差是 `1e-2`。

**根因**

`runner.load_error_tolerance()` 读 `tb_data_hls_error.json` 的 rmse/mae/mse，
取最大值当作"可接受误差"。但这个文件记录的是**数据集里参考实现（HLS 定点版）
相对软件黄金实现的偏差**：

```json
// polybench/2mm/tb_data_hls_error.json
{ "D": { "mae": 0.0, "mse": 0.0, "rmse": 0.0 } }
```

- 122 题里只有 28 题有这个文件；
- 官方评测器（`hls_eval/*.py`）**根本没有读它**，官方只看 csim 返回码；
- 把 mae/mse/rmse 混在一起取 max，量纲也不统一。

而且这个值算出来之后**只在提示字符串里用了一次**，从未参与判定——
`compare_dumps()` 里是硬编码的 `REL_TOL = 1e-2`。

**规避**

1. 改名为 `load_reference_error()`，**只作诊断**（提示参考实现自身的偏差量级），
   不再当作容差，也不写进给模型看的反馈。
2. `compare_dumps(got, ref, tol)` 显式接收容差，容差**按题目数值类型**选取：

   | 题目类型 | 判定方式 | 依据 |
   | --- | --- | --- |
   | 纯整数（CHStone 软浮点、MachSuite AES） | **精确比较**（tol=0） | 测试台本身就是位精确比对 |
   | 浮点 / 定点（polybench、定点变体） | 相对容差 1e-2 | 累加顺序不同会让末位有 1e-3 量级差异 |

   可用 `HLS_AGENT_DUMP_TOL` 覆盖。**整体口径只会更严不会更松**：
   整数题原来被 1e-2 的浮点容差放过去，属于漏判。
3. 判断类型用**真正的类型关键字**（`\bfloat\b` / `\bdouble\b` / `ap_fixed<`），
   不能用名字——CHStone 的头文件里写着
   `typedef unsigned long long float64;`，名字带 float 但本质是整数位模式。

**教训**

1. **数据文件的名字不等于它的语义**。用之前先弄清它是怎么产生的、谁在读它。
2. **"算了但没用到"是最隐蔽的一类 bug**：`tol` 被读出来、被格式化进字符串，
   看起来一切正常，唯独没进入判定。这类问题只有对着调用点逐个核对才发现得了。

## 22. 非零返回码不等于崩溃——把"算错了"当成"崩了"会给出错误的修复方向

**现象**

`fft_strided` 的报告写着「仿真程序崩溃」（返回码 4294967295），模型于是被引导去
查内存、指针、越界。但真实情况是：测试台打印了一串
`ERROR: 1010 (real): -182526263876.19 ...` 之后 `exit(-1)`——
**程序完整跑完了，是数值算错了**。

**根因**

`classify_run` 原来只按"返回码是否为 0"二分。而 HLS-Eval 里有两类测试台：

| 测试台类型 | 失败时的返回码 | 真实含义 |
| --- | --- | --- |
| PolyBench 风格（打 dump，从不检查数值） | 0 | 只能靠比对 dump 才知道对不对 |
| CHStone 风格（`main_result += (result != expected)`） | 不匹配的**用例数**（1、2、8、13…） | 测试不一致 |
| MachSuite / fft 风格（打印 `ERROR:` 后 `exit(-1)`） | 4294967295（= `exit(-1)`） | 测试不一致 |
| 真崩溃 | `0xC0000005` 访问违例、`0xC0000374` 堆损坏、`0xC0000135` 缺 DLL | 程序在跑完之前就死了 |

后两类在只看"是否为 0"时长得一模一样，但给模型看的修复方向**完全相反**。

**规避**

`errors.py::classify_run()` 按这个顺序判定：

1. 超时 → `TOOL_TIMEOUT`
2. `0xC0000135` 且零输出 → `ENVIRONMENT_ERROR`（进程没跑起来）
3. 输出里有 `Couldn't open input data file` 之类 → `INPUT_DATA_ERROR`
4. 返回码落在 `0xC0000000~0xC000FFFF`（Windows 异常码区间）→ `CSIM_RUNTIME_ERROR`
5. 返回码非 0 **且有输出** → `TEST_MISMATCH`（程序跑完了，是判定不一致）
6. 其余非 0 → `CSIM_RUNTIME_ERROR`

**为什么不能简单地用"高位是否为 1"判断**：`exit(-1)` 在 Windows 上就是
`0xFFFFFFFF`，高位同样是 1。必须用**异常码的具体区间** `0xC0000000~0xC000FFFF`，
才能把它和真的访问违例、堆损坏区分开。

**验证**

| 题目 | 真实返回码 | 修正前 | 修正后 |
| --- | --- | --- | --- |
| `fft_strided` | 4294967295（`exit(-1)`） | `CSIM_RUNTIME_ERROR` | **`TEST_MISMATCH`** |
| `dfadd` | 13 | `TEST_MISMATCH` | `TEST_MISMATCH`（返回码即失配用例数） |
| `dfmul` | 8 | 无分类 | **`TEST_MISMATCH`** |
| `aes_aes` | 3221226356（`0xC0000374`） | `CSIM_RUNTIME_ERROR` | `CSIM_RUNTIME_ERROR`（正确） |

**教训**

1. **"失败"要先问"程序跑到哪一步了"**，再问"为什么结果不对"。把这两件事混成
   一个"失败"，反馈给模型的信息就是错的，重试也是朝错误方向重试。
2. **返回码是可用的强信号**——CHStone 的返回码直接就是失配用例数，比任何日志
   分析都准。别浪费它。

## 23. `command -v python3` 成功不代表 Python 可用（应用商店占位程序）

**现象**

Windows 上执行 `bash run.sh atax`，脚本打印完标题行就**静默退出**，
什么都不做也没有报错；在资源管理器里双击批处理则是"窗口一闪就关"。

**根因**

Windows 10/11 自带一个"应用商店占位程序"：
`C:\Users\<你>\AppData\Local\Microsoft\WindowsApps\python3`（以及 `python`）。
它**存在于 PATH 中**，所以 `command -v python3` 会成功；但一执行就立刻退出，
退出码 **49**，不产生任何输出。

原来的入口脚本按 `command -v` 探测解释器，于是选中了这个占位程序，
后面的命令全部无声失败。这类"看起来没问题、其实什么都没发生"的故障最难查。

**规避**

探测解释器时**必须真的执行一次**，不能只看它存不存在：

```bash
pick_python() {
    for cand in python3 py python; do
        command -v "$cand" >/dev/null 2>&1 || continue
        if "$cand" -c 'import sys' >/dev/null 2>&1; then   # 真的跑一下
            printf '%s' "$cand"; return 0
        fi
    done
    return 1
}
```

`py` 是 Windows 官方启动器，不受占位程序影响，所以顺序是
**python3 → py → python**：容器里 `python3` 一击即中，Windows 上会落到 `py`。

**教训**

1. **"存在"不等于"可用"**。任何外部依赖的探测都要做一次真实调用，
   而不是检查路径或版本字符串。
2. 本机所有 Python 命令都应该用 `py`（见项目里的环境说明）；
   脚本里同样如此。
